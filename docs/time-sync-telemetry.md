# Time synchronisation and telemetry contract

FarmPi is the UTC clock authority. Every current telemetry payload carries `protocol_version`, `device_time_unix`, `clock_valid`, and `sample_seq` alongside the measurement catalogue. The HTTPS response always includes `server_time`; it adds `time_sync_required: true` when the node clock is unset/invalid or differs from FarmPi by more than 30 seconds. This is application-level acknowledgement data, intentionally independent of HTTPS, so the same fields and rule can be carried by a future LoRa ACK frame without changing database or backend semantics.

`received_at` is FarmPi's UTC receipt time and is the timestamp used for current/freshness and communication diagnostics. `observed_at` is the node's reported UTC observation time when the node clock was valid. An invalid/unset clock is never stored as 1970: `observed_at` falls back to the receive time and `clock_valid=false` records why. Out-of-tolerance reported observation time is retained, marked by `clock_out_of_tolerance`, and historical analytics deliberately use `received_at` for that row rather than treating the clock as trustworthy. `created_at` remains the MariaDB insertion/audit timestamp. `recorded_at` is retained as a compatibility alias for received time during the alpha migration.

`sample_seq` is unique per sensor node when present. A retry with the same `(sensor_node_id, sample_seq)` returns the original stored reading rather than creating another one. This is small but essential preparation for lossy/retried LoRa transport. Existing alpha rows and payloads remain readable; new firmware always sends version 1 and a sequence.

On boot, the ESP32 sends its first normal telemetry exchange with `clock_valid=false`; FarmPi returns authoritative time and the node then uses that time before relying on a local clock for its seasonal/daylight simulation. The first row is explicitly marked invalid-clock rather than inventing a 1970 observation.
